### 참고하는 방법

시뮬레이션 메커니즘이나 재질 값을 건드리기 전에 `noita-reference` skill(`.claude/skills/noita-reference`)을 씁니다.

- 메커니즘별로 읽을 절·문서·재질 필드와 연관 메커니즘은 skill의 [메커니즘 지도](../.claude/skills/noita-reference/references/mechanics.md) 한 곳에만 둡니다. 새 출처를 찾으면 거기에 추가합니다.
- 조회는 `go run ./tools/noitaref`로 합니다. 절(`section C49`), 문서(`doc MATERIAL_TICK`), 재질의 실제 값(`material water`), 키워드 검색(`search 액체 충격`)을 볼 수 있습니다.
- 재질의 실제 값은 엔진이 상속까지 처리해 읽어 들인 최종값입니다(`analysis-detail/runtime-completion/materials-expanded-analysis.json`). XML 선언값과 다를 수 있습니다.
- 결과는 메커니즘마다 `docs/briefs/`의 참고 요약으로 남깁니다.

### C50을 구현하지 않는 이유 (2026-11-06)

**C50이 하는 일:** 떨어지던 액체의 아래나 추가 낙하 칸에 다른 액체가 있고, 아래 조건이 모두 맞으면 C50이 발동합니다.
- 그 액체가 이번 틱에 아직 갱신되지 않았습니다. 마지막 갱신 틱(+2c)이 더 작습니다.
- 그 액체가 떨어지는 중입니다. 낙하 속도가 0보다 큽니다.
- 떨어지던 셀의 속도가 한 틱 가속분 이상입니다.

이때 떨어지던 셀을 격자에서 빼고, 프레임 뒤쪽 단계에서 위쪽 최대 129행 안의 빈 칸에 다시 넣습니다(C50:1331-1342, 1352-1363). 마지막 갱신 틱이 +2c라는 근거는 MATERIAL_TICK 4절과 C51:1406입니다.

**Noita에서 이 조건이 생기는 이유:**
- 작업 영역 안에서는 아래 행부터 갱신합니다(MATERIAL_TICK 2절). 그래서 바로 아래 셀은 보통 이미 갱신돼 있습니다.
- 작업 영역들은 (x mod 2, y mod 2) 네 그룹으로 나누고, 그룹 순서를 매 프레임 C 런타임 난수로 섞습니다(PRIORITY_RESULTS:24-25, C01:24).
- 그래서 아래 영역이 나중에 처리되는 프레임에는, 경계를 넘어 떨어지는 덩어리가 아직 갱신되지 않은 떨어지는 액체와 부딪힙니다.
- 실제 게임에서 306픽셀씩의 물·기름·모래 덩어리가 한 프레임에 57건을 냈습니다(C50:1382-1388).
- C50은 이 순서 차이로 생기는 충돌을 정리하는 장치입니다. 가만히 있는 액체(속도 0)에는 발동하지 않으므로 웅덩이 평탄화와는 관계없습니다.

**우리 순서에서는:** 청크 행을 아래부터 돌리고 행 안에서는 짝수 열 다음 홀수 열입니다(design.md 3절). C50 조건이 성립한 횟수를 세어 봤습니다(2026-11-06, 저장소 밖 임시 계측, 1 worker).

| 장면 | 막힌 액체 낙하 | 조건 성립 |
|---|---|---|
| 480×270 무작위 혼합, 600틱 | 약 768만 | 253 |
| 120×80 물 덩어리 낙하, 600틱 | 약 482만 | 294 |
| 높이 60에서 1600칸 붓기 | 약 11만 | 22 |
| 높이 200에서 1600칸 붓기 | 약 13만 | 95 |

- 조건이 성립한 경우는 대부분 추가 낙하 중 흩어지던 셀이, 같은 청크 행의 아직 처리되지 않은 이웃 청크로 넘어갈 때입니다.
- C50이 없으면 그 셀은 속도 0으로 한 틱 멈췄다가 다시 떨어집니다. 셀은 사라지지 않습니다.
- 스케줄러를 위쪽 청크가 먼저 돌 수 있는 방식(예: 4그룹)으로 바꾸면 이 결론은 무효이고, C50을 다시 검토해야 합니다.

### cgo 어댑터의 300개 상자 측정 (2026-11-07)

`internal/physics`(Box2D v3.2.0, `-O2`, worker 1개)로 잰 값입니다. 장면은 폭 38 m 상자 안에 크기 세 가지(변 0.5, 0.75, 1 m)와 각도 일곱 가지의 상자 300개를 20열 15줄로 놓고 떨어뜨립니다(`internal/physics` `newPile`). 한 번(op)은 Step 한 번(dt 1/60 s, sub-step 4)과 상자 300개의 위치·회전 읽기입니다. 게임이 틱마다 할 일입니다.

- falling: 떨어뜨린 뒤 300스텝(5초). 잠들기를 켜 둔 채 300스텝마다 장면을 새로 만듭니다.
- awake: 더미가 쌓인 뒤, 잠들기를 꺼서 모든 상자가 깨어 있는 최악의 경우입니다.
- `go test -run '^$' -bench . -count 5 ./internal/physics/`, 개발 PC(Ryzen 7 9800X3D, Windows, llvm-mingw clang 23.1.5), 5회 중앙값

| 경우 | AVX2(8칸) | SSE2(4칸) | 기준 CPU 추정(×2.5, AVX2) |
|---|---|---|---|
| falling | 84.3 µs | 91.8 µs | 0.21 ms |
| awake | 74.5 µs | 85.3 µs | 0.19 ms |
| 읽기만(300개, cgo 호출 600번) | 20.3 µs | | 0.05 ms |

- 기준 CPU(i5-7200U)에도 AVX2가 있어 AVX2 열을 씁니다. 추정은 design.md 2절의 방법입니다(단일 스레드 차이 약 2.5배). 16.7 ms 프레임 예산의 약 1.3%입니다.
- 읽기는 상자 하나에 cgo 호출 두 번이고 호출 하나가 약 34 ns입니다. 한 틱의 약 4분의 1이라, 읽을 몸체가 많아지면 Box2D의 이동 이벤트(`b2World_GetBodyEvents`)로 한 번에 읽는 방법을 봅니다.
- `-O3`는 차이가 없었습니다(falling AVX2 85.3, awake 74.6, SSE2 91.5/85.5 µs). 그래서 Box2D의 기본 CMake 릴리스 빌드(`-O3`)와 달리 cgo 기본값 `-O2`를 씁니다.
- 기준 CPU 실기와, 셀·강체·렌더를 합친 한 틱은 아직 재지 않았습니다(roadmap.md 4단계). 강체↔격자 연동(몸체의 픽셀을 지우고 찍기)이 더해지면 다시 잽니다.

### 결정성 (2026-11-07)

- Box2D v3.2가 밝힌 조건: 컴파일러가 곱셈과 덧셈을 FMA 하나로 합치지 않아야 합니다. Box2D의 CMake는 gcc와 clang에 `-ffp-contract=off`를 넘기고, 그 이유를 "기본으로 켜진 유일한 값 바꾸는 변환"이라고 적었습니다(v3.2.0 `CMakeLists.txt`, [Box2D 결정성 글](https://box2d.org/posts/2024/08/determinism/)). fast-math 류 설정은 쓰지 않습니다(우리 플래그에도 없음). 삼각함수는 C 라이브러리 대신 자체 근사를 씁니다(`b2ComputeCosSin`, `b2Atan2`). 그 글에 따르면 `atan2f`가 플랫폼마다 달랐고 `sqrtf`는 같았습니다. 비정규수를 0으로 바꾸는 CPU 모드가 켜져 있으면 결정성을 지원하지 않는다고 기록합니다(`physics_world.c` `b2CreateWorld`). Go 런타임은 그 모드를 켜지 않습니다.
- Go는 `#cgo CFLAGS`에 `-ffp-contract=off`를 허용하지 않습니다(`cmd/go/internal/work/security.go`의 허용 목록). 그래서 같은 규칙을 pragma로 겁니다(`internal/physics/box2d_fp.h`, pitfalls.md cgo 절). `TestCompiledWithoutContraction`이 컴파일러마다 확인합니다. 개발 PC의 clang 23.1.5는 pragma가 없으면 합쳤고(결과 2^-26), 있으면 합치지 않았습니다.
- SIMD 경로: Box2D는 실행할 때 AVX2(8칸)와 SSE2(4칸)를 고르고 arm64에서는 NEON(4칸)을 씁니다. `BOX2D_DISABLE_SIMD`로 컴파일하면 스칼라입니다. 개발 PC에서 AVX2, SSE2, 스칼라(`-tags box2dscalar`)가 600스텝 동안 같은 해시를 냈습니다(`internal/physics/testdata/determinism.golden`).
- 3개 OS(2026-11-07, PR #29의 CI): Windows(MinGW-Builds gcc 15.2.0), macOS arm64(Apple clang 21.0.0, NEON), Linux(Ubuntu gcc 15.2.0)에서 같은 골든이 통과했고, OS마다 스칼라 빌드도 통과했습니다. Windows와 Linux 러너는 AVX2 경로였고, 같은 실행에서 SSE2 경로도 AVX2와 같았습니다(ae7ea2d의 "box2d paths" 로그). 개발 PC의 clang 23.1.5까지 컴파일러 네 개입니다. `go run ./tools/check`의 "box2d paths" 단계가 OS, SIMD 경로, SSE2와 AVX2의 비교, FMA 탐침 결과를 로그에 남깁니다.
- race 단계에서 `internal/physics`는 1.2~1.4초입니다(CI). 가장 긴 패키지(`internal/game`, `internal/replay`, Windows 약 310~317초)에 비하면 작습니다.

### 강체↔격자 연동 측정 (2026-11-07)

몸체 450개 장면(design.md 2절, `internal/rigid` `BenchmarkBodies`)입니다.

- 480×270 방에 물 웅덩이와 모래 더미를 두고, 한 변 3~6칸의 나무 상자 450개를 30열 15줄로 떨어뜨려 3초(180틱) 돌립니다. 상자가 떨어져 서로, 모래, 물에 닿는 동안이라 거의 모든 몸체가 깨어 있습니다.
- 몸체당 픽셀은 평균 약 20개입니다. Noita 기지에서 한 프레임에 쓴 몸체 픽셀이 몸체당 약 18개였기 때문입니다(BODY_GRID_COUPLING:243-247).
- 셀 틱은 worker 2개(기준 CPU의 코어 수)이고, 몸체 단계는 한 스레드입니다.
- 시간은 성능 카운터로 잽니다. Windows의 `time.Now`는 0.5 ms 단위입니다(pitfalls.md).

`go test -run '^$' -bench Bodies -count 5 ./internal/rigid/`, 개발 PC(Ryzen 7 9800X3D), 5회 실행의 틱 900개를 합친 분포입니다(µs).

| 단계 | 중앙값 | p95 | 최대 |
|---|---|---|---|
| 몸체 쓰기(변환 읽기, 지우기, 쓰기, 대기열 넣기, 표시) | 224 | 251 | 473 |
| 지형 충돌(분류 비교, chain 재생성) | 133 | 228 | 483 |
| Box2D Step | 110 | 202 | 431 |

- 기준 CPU 추정(×2.5, design.md 2절): 몸체 몫 중앙값 1.15 ms, p95 1.47 ms, 최대 2.35 ms입니다. 측정 목표 3 ms(🧪, design.md 2절) 안입니다. 조인트, 지형 장면, 렌더, 실기는 아직 들어 있지 않습니다.
- Noita와 견주면: 기지 장면의 몸체 픽셀 단계가 중앙값 0.442 ms, p95 1.129 ms, 최대 1.847 ms였습니다(9800X3D, 계측 상태, 픽셀 중앙값 5,372, 몸체 297개, BODY_GRID_COUPLING:237-252). Step은 중앙값 0.43 ms였습니다(RIGID_BODY_LOAD_DESTRUCTION:83-91). 우리 쓰기 단계는 같은 일(지우기·쓰기·밀어내기·표시)에 Box2D에서 변환을 읽는 cgo 호출 450번(약 16 µs)이 더해진 값입니다.
- 위 표는 몸체 픽셀을 앞쪽 사상으로 쓰던 때입니다. 역사상으로 바꾼 뒤는 아래에 있습니다.
- 지형 단계는 처음에 셀마다 블록을 찾아 분류해 중앙값 약 280 µs였습니다. 블록 안의 행을 한 번에 읽게 바꿔 약 135 µs가 됐습니다(`World.Classify`). 몸체가 픽셀을 쓰면 그 청크의 버전이 올라 분류를 다시 계산합니다. 몸체 셀은 분류가 열림이라 재생성은 드뭅니다.

셀 틱의 전후입니다. 쉰 틱 수(design.md 4절)와 틱마다의 대기열 확인이 더해졌습니다. 개발 PC, 5회 중앙값이고, 전은 `origin/main`(1f3cd5a)입니다.

- Checksum은 셀마다 쉰 틱 수를 더 섞어 10% 느려졌습니다. 테스트와 리플레이 확인에만 씁니다.
- 로드 직후 장면이 빨라진 것은 틱당 작업 예산(3절) 때문입니다. 자리를 잡아 가는 모래가 화면 가까이에서 20틱 동안 깨어 있어 예산의 일부를 쓰고, 그만큼 무거운 먼 청크가 더 기다립니다. 1 worker로 61틱 동안 돈 청크는 7,911 → 7,733번, 미룬 청크는 4,476 → 5,022번(+12%)이었습니다. 틱이 싸진 대신 먼 곳이 조금 더 늦게 움직입니다.

### 부력과 액체 접촉 저항 (2026-11-08)

Noita의 64×8 나무 조각 시험(C31:538, 544-546)을 같은 크기로 재현했습니다(임시 테스트, 저장소 밖). 256×300 방에 물 210칸 깊이, 64×8 나무를 40행에서 떨어뜨려 43틱에 물에 닿습니다. 아래는 몸체의 아래쪽 속도(m/s)입니다. Noita 값은 240프레임의 vy(px/s)를 10으로 나눈 것입니다.

### 몸체 안의 정착 모래 (2026-11-08)

기운 채 쌓인 상자에 모래를 부으면 상자끼리 파고들던 것의 원인과, 몸체에 파고드는 새 정착 칸을 지형에서 뺀 전후입니다(design.md 8절).

재현: 192×160 방, 돌 바닥 위로 16×12 상자 셋을 높이를 달리해 떨어뜨리고, 240틱부터 1600틱까지 틱마다 50×3칸에 모래를 부어 2000틱 돌립니다. 상자 위치를 바꾼 12개 배치 가운데, 서로 기운 채 쌓인 하나(위치 (77, 100), (91, 70), (72, 40), `TestStackUnderSandStaysApart`)에서 두 상자가 속도 거의 0인 채로 파고들어 315틱 0.5칸에서 1158틱 12.3칸이 됐습니다. 나머지 11개는 붓는 동안 0.2칸 미만입니다.

| 변형(임시, 저장소 밖) | 붓는 동안 두 몸체의 최대 겹침 |
|---|---|
| 그대로 | 12.3칸 |
| 지형을 다시 만들어도 몸체를 깨우지 않음 | 12.3칸 |
| 윤곽 단순화를 끔 | 10.8칸 |
| 몸체 칸 안(칸 중심이 몸체 안)의 정착 모래만 지형에서 뺌 | 6.1칸 |
| 정착 모래를 지형에서 아예 뺌 | 0.07칸 |
| 몸체 모양에 0.1칸 넘게 파고드는 새 정착 칸을 뺌(채택) | 0.49칸(착지 때 생긴 겹침, 더 커지지 않음) |

- 원인은 정착 모래로 만든 지형이 몸체 모양 안에 생기는 것입니다. 몸체 칸 안에 막힌 모래와 기운 변을 넘는 칸 모서리가 절반씩 몫을 합니다.
- 채택한 규칙으로 12개 배치의 다른 결과(겹침, 착지)는 그대로이고, 오래 자리 잡은 모래 바닥에 0°·30°·45°로 떨어뜨린 상자의 멈춘 높이도 같습니다.
- 몸체 450개 장면에서 지형을 다시 만든 횟수는 180틱 동안 228 → 186번, 분류 계산은 4,458번으로 같습니다. 판정에서 뺀 칸은 2,207번입니다.
- 착지 순간의 겹침(0.7~2.3칸)은 별개입니다. 초속 11.6 m로 떨어진 상자가 다른 상자에 1.3칸 박혔다가 초당 11 rad로 돌며 밀려났습니다. Box2D v3는 움직이는 몸체끼리 연속 충돌을 하지 않고 투기 접촉 거리가 0.02 m(0.2칸)라, 한 틱에 그보다 많이 다가오면 박힙니다.

| 단계 | 전 중앙값 / p95 / 최대 | 후 중앙값 / p95 / 최대 |
|---|---|---|
| 몸체 쓰기 | 240 / 338 / 791 | 240 / 327 / 793 |
| 지형 충돌 | 137 / 239 / 695 | 167 / 277 / 758 |
| Box2D Step | 120 / 229 / 642 | 119 / 210 / 637 |
| 몸체 몫 합계 | 494 / 705 / 1176 | 517 / 707 / 1222 |
| 셀 틱(worker 2개) | 211 / 350 / 840 | 199 / 315 / 793 |

- 지형 단계는 근처 몸체마다 그 범위의 정착 칸을 판정하는 몫만큼 늘었습니다(+30 µs). 몸체 몫 합계는 +23 µs(+5%)이고, 두 차례 각각은 0%와 +9%로 흔들렸습니다. 기준 CPU 추정(×2.5) 약 1.3 ms입니다.

## 4. The Powder Toy 소스

위치: `C:\Users\tongm\Downloads\the-powder-toy-analysis` (저장소 밖). 릴리스 v100.1.400(태그 `v100.1.400`, 커밋 `d768aeb`)의 소스 사본이고 git 저장소는 아닙니다. 라이선스는 GPL-3.0입니다.

- **역할:** Noita 분석 자료에 없거나 확인되지 않은 부분을 우리 설계로 메울 때 보는 보조 참고입니다. 해당 분야는 압력과 공기 흐름, 열전도, 상태 변화, 기체 확산, 전기입니다. Noita 관측 규칙이 있으면 그것이 우선입니다.
- **쓰는 법:** `noita-reference` skill의 9단계(빈칸)에서만 봅니다. 메커니즘별 파일과 함수는 skill의 [TPT 지도](../.claude/skills/noita-reference/references/tpt.md) 한 곳에만 둡니다.
- **라이선스:** 코드, 주석, 원소 표를 옮기거나 Go로 번역하지 않습니다. 옮기면 matter-wake가 GPL 파생물이 됩니다. 방식만 이해하고 자기 말로 설계합니다. 참고 요약에는 "TPT 방식"으로 출처를 표시합니다.
- **구조가 다른 점:** TPT는 float 입자 배열을 한 스레드에서 배열 순서대로 갱신합니다. 압력, 공기 속도, 주변 온도는 4×4 픽셀 격자에 둡니다. 이동은 위쪽으로도 쓰고 최대 30칸까지 훑습니다. 원소 이름으로 분기하는 예외도 많습니다. 우리 제약(정수, 청크 행 병렬, `MaxReach`, 위로 쓰기 없음, 이름 분기 없음)에 맞춰 다시 설계해야 합니다.
- **수치:** TPT 고유 단위(켈빈, ±256 압력, 자체 화면 기준 중력)라 그대로 비교할 수 없습니다. 하나를 🧪 초기값의 근거로 쓸 때는 이 문서에 파일과 함수를 적습니다.
